# Create Effect

TENKIKAIの共通エフェクトを、用途別設定StateDefと変数駆動の共通実行StateDefで設計・実装する。

## 規約を読む

作業前に次を読む。

1. `AGENTS.md`
2. `docs/design/effect/AGENTS.md`
3. `docs/AGENTS.effect.md`
4. `docs/design/008-effects.md`
5. 対象の`docs/design/effect/NUM-*.md`
6. 対応する`docs/state/`文書と変数文書

技からの発出条件、入力、攻撃または技本体も変更する場合は`create-waza`を併用する。共通エフェクト自体の表現、番号、変数契約および実行構造は本スキルで管理する。

## 現状を調査する

`rg`で次を照合する。

- 使用中の1000番予約範囲、StateDef、Helper ID、Explod ID、Projectile ID
- Action、Sprite、AIRの透過指定
- 用途別出現StateDefと末尾`900`〜`999`の共通StateDef
- Helperの`var`・`fvar`割当
- CNSへ直接記述された時間、速度、加速度、倍率、角度、周期、色、透明度、優先順位
- 設計文書、State文書および実装の差異

CNS実装と文書に差異がある場合はCNSを正本とし、CNSの動作と数値を変更せずに文書を同期する。確定済み要求とユーザーの指示に従い、WinMUGEN固有仕様を推測で補わない。

## 責務分解の承認を得る

新規エフェクトを作成する前に、既存エフェクトとの責務分解が正しいかを検討し、ユーザーへ提示して明示的な承認を得る。

次を整理する。

- 作用対象：全画面、背景、キャラクター、特定Helper・Projectile、局所座標
- 表現手段：`AllPalFX`、`BgPalFX`、`PalFX`、Helper、Explod、Projectile、AfterImage
- 発動元、位置基準および寿命管理者
- 他エフェクトとの同時成立、優先、置換関係
- 複数用途から共有する責務
- 既存エフェクトの新しい用途別パターンとして収容できるか
- 独立した設計文書および1000番予約範囲が必要か
- 既存大項目の共通モデルへ個別数値だけを渡して表現できるか

責務の違いは名称、色または素材だけで判断しない。作用対象、管理責務および再利用単位が同じ場合は、原則として既存エフェクトの用途別パターンとして提案する。作用対象または管理責務が異なる場合は、独立エフェクトとして提案する。

既存大項目へ用途別パターンを追加する場合は、用途別出現StateDefが個別数値を保存し、その大項目の既存共通モデルへ遷移する構造を維持する。新しい表現を既存の変数契約で表現できない場合は、全用途から利用できる変数駆動の機能として共通モデルを拡張する。用途別パターン専用の共通実行StateDefを追加してはならない。

承認前に次を行わない。

- `docs/design/008-effects.md`への確定登録
- 個別設計文書の新設または責務変更
- StateDef予約範囲、Helper IDまたはExplod IDの確定
- CNS・AIRへの実装
- 既存エフェクトから新規エフェクトへの処理移動

ユーザーが責務分解を承認した後に、設計登録と実装へ進む。既存エフェクトの責務を再分解する場合も同じ承認工程を適用する。

## 設計を登録する

新規エフェクトまたは新しい表現パターンは、実装前に`docs/design/008-effects.md`と個別設計文書へ登録する。

Helper型エフェクトへ1000番単位のStateDef範囲を割り当てる。

- 末尾`000`〜`899`：用途別出現StateDef
- 末尾`900`〜`999`：共通実行、共通管理、共通寿命、共通終了StateDef

左右、前後、前面・背面などを別Helperで描画する場合は、必要な数の共通StateDefを末尾`900`〜`999`へ配置する。

末尾`900`〜`999`に複数のStateDefを置く場合も、それらは一つの論理的な共通モデルを処理分割したものでなければならない。左右や前面・背面などの同じ構成要素は、どの用途別パターンでも同じ処理関係を通す。用途別パターンごとに異なる実行モデルを選択させない。

## 用途別出現StateDefを実装する

用途別出現StateDefで、その用途を完成させる全調整値をHelper自身の`var`・`fvar`へ保存する。

対象にはAction選択、時間、寿命、位置、速度、加速度、倍率、補間、角度、回転、周期、振幅、合成、透明度、色、描画優先順位、AfterImage、ExplodおよびProjectile設定を含める。

初期化後、同じtickに対応する共通StateDefへ遷移する。Root変数を引数領域として使用しない。

## 共通実行StateDefを実装する

共通StateDefは用途別出現StateDefが保存した値だけを参照する。

- 用途番号、発出元StateDefまたはRootの技状態で調整値を分岐しない
- 調整用の固定値を直接記述しない
- 出現、維持、消滅を保存時間とHelper経過値から判定する
- 必要なら末尾`900`〜`999`内で複数の共通処理を固定順に通す
- 共通寿命、Explod除去、Projectile停止およびHelper終了を同じ予約領域で管理する

新しい用途別パターンに既存共通モデルが対応できない場合、別の実行StateDefへ分岐させる前に、時間区間、補間方式、開始値、目標値および終了値などを変数化して共通モデルを拡張する。共通モデルとして統合できないと判断した場合は、作用対象、管理責務および再利用単位を再検討し、別大項目へ分割するかをユーザーへ確認する。

式の定数として不可避な単位変換値を除き、ユーザーが調整し得る値はすべて用途別出現StateDefへ置く。

## 既存表現を移行する

構造だけを移行する場合は、見た目を変更しない。

1. 移行前の各直値と式を列挙する。
2. 同じ値を用途別出現StateDefの変数へ保存する。
3. 共通StateDefの式を変数参照へ置換する。
4. 移行前後の完成値、時間境界、生成数、座標、速度、倍率、色、透過および優先順位を比較する。
5. 構造変更と表現調整を混在させない。

## 文書と検査

実装と同時に、StateDef、遷移、変数、IDを`docs/state/`へ同期する。変数割当を含めてCNSを正本とし、対象Helperの変数文書を現行実装へ合わせる。

個別設計文書のファイル名とH1は、最初の用途別パターン名ではなく大項目名にする。同じ大項目の用途別パターンを別の個別設計文書へ分散させない。

実機微調整中もCNSまたはAIRの現行値を設計文書とState文書へ同期し、試験中と注記する。ユーザー検収後は値を維持し、状態の注記を確定結果へ更新する。

最後に次を行う。

1. 予約範囲、ID、Actionおよび変数の衝突確認
2. CNSに残る調整用直値の監査
3. `make check`
4. `git diff --check`
5. WinMUGEN実機で確認する表示と操作の提示
