# 技仕様文書の作業規則

## 責務

`docs/attacks/`は、技の自然言語要求を、実装前に完全な技仕様へ解決するための正本である。個別技の美的意図は`docs/design/`、実装済みStateDefの記録は`docs/state/`が担う。

技仕様は[階層スキーマ](structure.md)、[仕様解決規則](specification-resolution.md)、[State Controller対応](state-controller-map.md)に従う。

## 入力と記録形式

- ユーザー入力は自然言語で受ける。JSONまたはYAMLの入力を要求しない。
- 技仕様の正本はMarkdownとする。JSONまたはYAMLを正本にしない。
- ユーザーの表現を「ユーザー要求」として残し、その後に固定見出しを用いた「解決済み仕様」を記録する。
- 機械処理用データが必要になった場合も、ユーザー承認なしにMarkdownの正本を置き換えない。

## 仕様解決

解決順序は次のとおりとする。

```text
既存の確定事項
→ ユーザー指定
→ ユーザーが明示承認した試験値
→ TENKIKAI固有規約による実装制約
```

`common-v1`、分類プロファイルおよびKFM値を自動適用しない。後段を優先する。ただし、TENKIKAI固有規約による実装制約がユーザー指定と衝突する場合は、自動変更せずユーザーへ提示する。

実装開始前に、全項目を次のいずれかへ解決する。

- ユーザー指定
- 対象外
- ユーザー承認済み

未確定事項は必ずユーザーへ質問し、「未指定」のまま実装してはならない。推測、一般的なゲーム慣習、KFM値、`common-v1`または分類プロファイルで補完してはならない。ユーザーが回答しないことを承認とみなさない。「対象外」は技の構造上その項目を持たない場合、「なし」はユーザーが機能を付与しないと確定した場合に使用する。

試験実装が目的の場合に限り、版名、適用項目および具体値を提示してデフォルト候補を採用してよいか質問できる。明示承認された項目だけを「ユーザー承認済み」の試験値として記録し、確定値として扱わない。

Power関連は、ユーザーが具体値を指定するか、独立して提示された試験値を明示承認した場合だけ扱う。未承認の場合は値や「なし」を仕様へ補わず、分類デフォルトまたはKFM値から推論せず、実装にもPower処理を追加しない。既存技にあるPower処理は、ユーザーの明示指示なしに変更または削除しない。

## KFM試験候補

試験実装用の数値候補は`../kfm/kfm.cns`および`../kfm/kfm.cmd`を根拠とする。KFMに対応実装がない機能について数値や挙動を推測しない。

- KFM値はユーザーへ提示できる試験候補であり、技仕様へ自動適用したり、KFMのStateDefをTENKIKAIへそのまま移植したりしない。
- KFMのAction、座標、Clsn、発生・持続・後隙は素材に依存するため、CNS値だけから推測しない。
- KFMにProjectileおよびReversalDefの実装例はない。該当技は個別承認を必要とする。
- ユーザーが試験用デフォルトを承認した場合だけ、版名、対象項目および具体値を記録する。既存技へ将来の新版を自動適用しない。

## 承認を必須とする機能

次の機能はデフォルトから推論せず、実装前にユーザー承認を得る。

- ガード不能、ガードクラッシュ
- アーマー貫通・破壊、無敵貫通
- Projectile防御・相殺貫通
- ReversalDef
- 長時間または完全な無敵
- 相手のStateを奪う処理
- 即死級ダメージ
- 外部キャラクター固有のVar、Helper、独自防御仕様への依存

防御突破特性は有無だけで記録しない。無視、軽減不適用、消費、破壊、ダメージ通過など、作用を具体的に記録する。

## 個別技文書

個別技は`NUM-name.md`として1技につき1文書を作る。H1は`# NUM: 技名`形式とし、`NUM`はファイル名先頭の番号と一致させる。

個別技文書は、少なくとも次の順序で記載する。

1. 基本情報
2. ユーザー要求
3. 解決済み仕様
4. 演出と攻撃定義の同期
5. 実装対応

CNSは現在の技実装の正本、個別技文書はユーザー要求と解決済み仕様の記録として扱う。ユーザーが承認した試験候補は解決済み仕様の候補として記録できるが、実機微調整で変更した未検収値を個別技文書へ転記しない。検収後に確定した値と挙動を反映する。試験中のCNSと技文書の差異は自動同期せず、検収済み仕様との差異は報告して指示を待つ。
