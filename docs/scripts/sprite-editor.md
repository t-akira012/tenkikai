# Sprite Editor方針

## 目的

`assets/`に置いたPNG画像を、macOSのCLIだけでWinMUGEN用の`binary/sprite.sff`へ追加できるようにする。既存のSFFを破壊せず、追加した画像をAIR定義から利用できる状態にする。

## 正規ソースと生成物

スプライトの正規ソースは、次のテキスト・画像ファイルとする。

```text
assets/sprite.json
assets/sprites/*.png
```

`assets/sprite.json`には、各画像のグループ番号、画像番号、原点、パレット、透明色などのSFF定義を記録する。画像本体は`assets/sprites/`へ個別のPNGとして保存する。外部から取得した非共有パレットPCXは、個別素材ディレクトリにPCXのまま保存して参照してよい。番号定義はバイナリSFFを直接編集せず、JSONの変更として行う。

`binary/sprite.sff`は生成物とし、正規ソースから毎回再生成する。生成物を直接編集してはならない。

SFFからPNGへ展開する際は、サブヘッダーのパレット共有フラグを読み取る。パレットを共有しないスプライトにはPCX内の固有パレットを適用し、共有するスプライトには共有元スプライトのパレットを適用する。画素インデックス0は透明としてアルファへ反映する。外部のACTパレットをSFF展開へ一律に適用してはならない。SFFの画素値を8-bitグレースケールPNGとして保存してはならない。

パレット共有フラグと共有元の情報はJSONへ保存し、SFFへ再構築する際にも維持する。共有状態を無視して一律にACTを適用してはならない。

### 本リポジトリ固有の共有規約

WinMUGENの仕様そのものではなく、本リポジトリのSFF生成時だけに適用する規約として、先頭スプライトを共有元パレットとして個別格納し、2枚目以降でグループ番号が`10000`未満のスプライトはパレット共有フラグを有効にする。グループ番号が`10000`以上の素材は個別パレットとして扱い、共有フラグを無効にする。JSONに保存された個別の`palette_shared`値より、この規約を優先する。先頭まで共有にするとWinMUGENが参照できる共有元パレットがなくなり、共有スプライトが黒くなる。

共有フラグが有効なスプライトより前に共有元パレットが存在しない場合は、構成分析用に保存した`docs/scripts/pallet.act`を基準とする。

JSONからSFFへ再構築する際、グループ番号が`10000`未満の共有スプライトは、`docs/scripts/pallet.act`を基準にした画素インデックスで符号化する。共有スプライトをPNG固有のパレットで符号化してはならない。グループ番号が`10000`以上の個別スプライトだけは、入力PNGのパレット、またはJSONのパレットを使用する。

### 構成分析用パレット

`docs/scripts/pallet.act`は、Windows上のSFF AIR EDITORで出力した ACT FILE を保存したものである。WinMUGENの共有スプライトが使用する色番号と色値の対応を分析するための正本であり、色を低い番号へ詰め替えたり、`pallet-maker`で再生成したりしてはならない。特に本パレットでは、元スプライトの色が高位のインデックスに配置されているため、インデックス番号を保持する。

PNGをSFFへ符号化する際は、アルファが0の画素に加え、画像左上1pxのRGBと一致する画素も透明インデックス0へ割り当てる。アルファを持たない素材のグリーンバック等を、WinMUGEN用の透明色として扱うためである。

`assets/effects/`の個別パレット素材は共通パレット処理の対象外とし、JSONではグループ`10000`の画像番号`0`から連番で登録する。画像パスは`effects/`から始め、SFF生成時は`assets/sprites/`を基準にした相対パスが解決できない場合に`assets/`直下も検索する。

非共有パレットPCXをJSONからSFFへ構築する場合は、PCXの画素インデックスと固有パレットを再量子化せず、そのままSFFへ格納する。PCXでは画素インデックス`0`を透明色として扱い、PNG用の左上RGB透明化を適用しない。

既存SFFの展開は次の形式で行う。

```text
binary/sprite.sff
  ↓ sff-to-json
assets/sprite.json
assets/sprites/*.png
```

再構築は次の形式で行う。

```text
assets/sprite.json + assets/sprites/*.png
  ↓ json-to-sff
binary/sprite.sff
```

同じJSONと画像から同じスプライト構成を再生成できることを目標とする。SFFのバイナリ配列や内部オフセットの一致ではなく、画像、番号、原点、パレット、透明色などの意味的な一致を保証する。

## 試作の範囲

試作では、次の処理だけを対象にする。

1. 既存SFFを`assets/sprite.json`と`assets/sprites/`へ展開する。
2. `assets/sprites/`内のPNGの透明部分を判定し、SFFで扱えるインデックス画像へ変換する。
3. JSONで指定した番号・原点・パレットに従ってSFFを再構築する。
4. 既存スプライトを保持したまま、新規スプライトを追加する。
5. 再構築後のSFFを検査し、JSONと画像の定義が反映されていることを確認する。

試作段階では、元の`binary/sprite.sff`を直接上書きしない。作業用のコピーへ出力し、形式検査と画像数・画像番号・サイズの確認が完了した後に置換可能とする。既存SFFを正規ソースへ展開した後は、SFFではなくJSONとPNGを編集する。

## SFFの扱い

初回の`binary/sprite.sff`を入力として使用し、SFFのバージョン、スプライト一覧、パレット、画像データの格納方式を読み取って正規ソースへ展開する。以後は`assets/sprite.json`と`assets/sprites/`を入力として使用する。

新規画像は既存SFFの形式に合わせて追加する。PNGのアルファチャンネルはそのまま格納せず、SFFの透明色およびパレットインデックスへ変換する。既存画像のグループ番号・画像番号・原点は変更しない。

## CLIツールの責務

ツールは、次の確定済みオプション形式で入出力を指定する。SFFからの展開結果は`dist/`へ出力し、編集用の`assets/`を上書きしない。

```console
sff-to-json \
  --input binary/sprite.sff \
  --output-json dist/sprite.json \
  --output-png dist/sprites/

json-to-sff \
  --input-json assets/sprite.json \
  --input-png assets/sprites/ \
  --output binary/sprite.sff
```

入力画像の順序と割り当て結果を端末へ表示し、処理対象・現在の画像・完了・失敗を隠さない。

画像変換とSFF入出力を分離し、PNGの透明化だけを再実行しても既存SFFへ影響しない構成にする。既存SFFのバックアップはツール内で削除せず、出力先を分けて保持する。

## 検証

試作ツールは次を検証する。

- 入力PNGが存在し、読み込み可能であること。
- 透明部分が検出され、透明色として一貫して変換されること。
- 画像サイズがSFFへ格納可能であること。
- 既存SFFのヘッダーと既存スプライト数が追記前後で維持されること。
- 新規画像のグループ番号・画像番号・原点が指定値と一致すること。
- 出力SFFがWinMUGENから読み込める形式であること。

macOS上ではバイナリ構造と画像データの検査まで行い、実際の描画とAIRからの参照はWindows上のWinMUGENで確認する。

## 復旧

試作出力に問題があった場合は、commit済みの`binary/sprite.sff`へ戻せるようにする。元ファイルを直接編集せず、検証済み出力だけを明示的に置換する。
